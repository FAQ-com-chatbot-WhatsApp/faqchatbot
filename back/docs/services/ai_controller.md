# Implementation Plan: AI Controller (`ai_controller.py`)

## 1. Description
The AI Controller serves as the primary API gateway for all Artificial Intelligence-related operations. It exposes endpoints for processing inbound messages, retrieving AI performance statistics, and managing conversation context within the vector database. Its main purpose is to orchestrate the interaction between the API layer and the core AI services, such as the `ConversationOrchestrator`.

## 2. Architecture and Design
This controller is a key component of the API Layer in the system's Clean Architecture.
- It receives HTTP requests and translates them into calls to the appropriate business logic services.
- It defines Pydantic schemas (`ProcessMessageRequest`, `AIStatsResponse`, etc.) to validate incoming data and serialize outgoing responses, ensuring a clear and robust API contract.
- It relies on FastAPI's dependency injection system to get instances of services and repositories (e.g., `get_conversation_orchestrator`, `get_sync_session`).

## 3. Data Structure
- **`ProcessMessageRequest`**: The input schema for the main message processing endpoint. It requires `chat_id`, `phone_number`, and `message_text`.
- **`ProcessMessageResponse`**: The output schema after processing a message. It returns the `conversation_id`, a boolean `response_sent`, the `response_text` generated by the AI, the detected `intent`, and the updated `maturity_score`.
- **`AIStatsResponse`**: The output schema for the AI statistics endpoint, providing metrics like total conversations, LLM interactions, tokens used, average latency, and the number of documents in ChromaDB.

## 4. Dependencies and Integrations
- **`fastapi.APIRouter`**: Used to define and organize the endpoints.
- **`ConversationOrchestrator`**: The primary dependency, this service contains the core business logic for handling the entire conversation flow.
- **`ConversationRepository` & `LLMInteractionRepository`**: Used by the `/stats` endpoint to query the database for performance metrics.
- **`ChromaDB Client`**: Used to get statistics about the vector store.

## 5. Use Cases
- **Use Case 1: Processing a New Patient Message:** A webhook from the WAHA gateway calls the `POST /ai/process-message` endpoint. The controller receives the patient's message, passes it to the `ConversationOrchestrator`, and returns a JSON response detailing the AI's reply and the conversation's new state.
- **Use Case 2: Monitoring AI Performance:** An administrator accesses the analytics dashboard, which calls the `GET /ai/stats` endpoint. The controller gathers data from multiple repositories and the ChromaDB client to provide a real-time snapshot of the AI's performance and usage.

## 6. Security
- The endpoints in this controller are presumed to be protected by authentication and authorization middleware applied at a higher level in the application (e.g., in `api_router` or the main `app`).
- Input validation is handled by Pydantic, which helps prevent common injection-style vulnerabilities.

## 7. Performance
- The `/process-message` endpoint is asynchronous (`async def`) because it depends on the `ConversationOrchestrator`, which performs I/O-bound operations (database calls, external API requests to Gemini). This allows the server to handle other requests while waiting for these operations to complete.
- The `/stats` endpoint performs several database queries and could become slow with a large volume of data. Caching strategies could be implemented here if performance becomes an issue.

## 8. Testability
- **Unit Testing:** The controller's logic can be unit-tested by mocking the `get_conversation_orchestrator` and other repository/service dependencies. This allows for testing the request/response handling in isolation.
- **Integration Testing:** End-to-end tests can be written to simulate HTTP requests to the endpoints and verify that the entire flow—from controller to service to database—works as expected.

## 9. Error Handling
- The controller uses a generic `try...except` block to catch any exceptions that occur during the execution of the `ConversationOrchestrator`.
- If an error occurs, it raises an `HTTPException` with a `500 Internal Server Error` status code, providing a clear error message to the API client while preventing the application from crashing.

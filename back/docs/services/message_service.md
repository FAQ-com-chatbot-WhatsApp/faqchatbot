
# Feature: MessageService

## 1. Description

The `MessageService` is the service layer responsible for all CRUD (Create, Read, Update, Delete) operations for messages. It orchestrates the business logic for handling different types of messages (text, media, location) and integrates with other AI services (`TranscriptionService`, `DescriptionService`) to automatically enrich media messages with metadata, transcriptions, and visual analysis.

## 2. Architecture and Design

-   **Message Type Orchestration:** The `create_message` method acts as an orchestrator that identifies the type of message received (`MessageCreateText`, `MessageCreateMedia`, etc.) and delegates the creation to the appropriate method in the `MessageRepository`.
-   **Automatic Media Enrichment:** The main design feature is the automatic enrichment of media messages during their creation:
    -   **Voice (`voice`):** The audio is automatically transcribed using the `TranscriptionService`.
    -   **Video (`video`):** The video's audio is transcribed, and basic metadata is generated from the file name.
    -   **Image (`image`):** The image is analyzed by the `DescriptionService` (which uses the `VisionService` with BLIP-2) to generate a title, description, and tags.
    -   **Document (`document`):** Basic metadata is generated from the file name and caption.
-   **Dependency Injection:** The service receives a SQLAlchemy session (`db: Session`) and instantiates its own dependent repositories and services (`MessageRepository`, `DescriptionService`, `TranscriptionService`).
-   **Pydantic Schemas:** The service uses Pydantic schemas for input (`MessageCreate...`) and output (`MessageOut...`), ensuring data validation and clear API contracts.

## 3. Data Structure

The service handles multiple models and schemas:
-   **`MessageModel`:** The main SQLAlchemy model representing a message in the database.
-   **`MediaModel`, `LocationModel`:** Related models that store the specific data for each message type.
-   **Creation Schemas (`MessageCreate...`):** Define the structure of the data needed to create a new message.
-   **Output Schemas (`MessageOut...`):** Define the structure of the data returned by the API, ensuring that only relevant information is exposed.

## 4. Dependencies and Integrations

-   **`MessageRepository`:** The data access layer for all message persistence operations.
-   **`DescriptionService`:** Used to generate metadata for images and other files.
-   **`TranscriptionService`:** Used to transcribe voice and video messages.
-   **`ConversationOrchestrator` (implied):** The conversation orchestrator is the primary consumer of this service, calling `create_message` to save each received or sent message to the database.

## 5. Use Cases

-   **Receiving a Text Message:** The webhook receives a text message. The `ConversationOrchestrator` calls `message_service.create_message` with a `MessageCreateText` payload. The service saves the message and returns it.
-   **Receiving a Voice Message:** The webhook receives an audio message. The `ConversationOrchestrator` calls `create_message` with a `MessageCreateMedia` payload of type `voice`. The `MessageService` invokes the `TranscriptionService` to get the text from the audio and then saves the media message along with its transcription to the database.
-   **Receiving an Image:** The webhook receives an image. The `ConversationOrchestrator` calls `create_message` with a `MessageCreateMedia` payload of type `image`. The `MessageService` invokes the `DescriptionService`, which in turn uses the `VisionService` to analyze the image. The message is saved with the title, description, and tags generated by the AI.

## 6. Security

-   The service validates that for media messages, a file URL (`file.url`) is provided. This URL should be generated by a secure external process (e.g., upload to S3 storage), and the `MessageService` only stores the reference to it.

## 7. Performance

-   Creating media messages, especially voice and image, can be a slow operation due to the need for AI processing (transcription and visual analysis). To optimize, these enrichment operations could be moved to background jobs (queued in RQ), allowing the message to be saved quickly and enriched asynchronously. The current implementation appears to be synchronous.

## 8. Testability

-   The service can be tested by mocking its dependencies (`MessageRepository`, `DescriptionService`, `TranscriptionService`).
-   It is possible to test each message creation flow (text, voice, image, etc.) to ensure that the correct enrichment services are called and that the data is passed properly to the repository.

## 9. Error Handling

-   **`NotFoundException`:** Thrown if a read, update, or delete operation is attempted on a message that does not exist.
-   **`ValueError`:** Thrown if an invalid message type is provided or if an update is incompatible with the existing message type.
-   **AI Service Failures:** Exceptions from the transcription and description services are caught (`try...except`), and an error is logged. The system then proceeds without the enrichment, ensuring that a failure in an AI component does not prevent the message from being saved.
